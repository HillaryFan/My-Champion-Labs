# 從湧現的關係能力到可靠的健康陪伴產品基礎設施

**公開改編版 P1｜整理日期：2026-09-17｜原 Markdown 未宣告內容版本或日期。**

本文件是去識別化產品化分析，不取代 V2 主提案與 V2 Addendum。以下觀察由來源作者陳述；本次公開整理未獨立檢查底層對話紀錄，也未核實已部署能力或參與者成果。

## 目的與結論

本備忘錄說明長期 AI 對話中偶爾能形成的互動能力，與一般使用者可以信任的健康陪伴產品之間，仍然存在什麼差距。來源作者描述，長期互動中，通用模型在特定條件下可能同時呈現關係溫度、工作承擔、健康追問、選擇性記憶與保守升級處置。這些敘述形成值得測試的可行性假設，尚不能建立可行性、產品可靠性或臨床安全。

正式產品不能要求每位使用者花數月時間教會一條對話如何工作。研發團隊必須把已觀察到的行為轉成明確架構、政策、測試與復原機制，使它們在不同使用者、模型更新與上下文衰退後仍能維持。

## 原型互動顯示的可能能力

來源作者描述，長期互動軌跡曾在不同時點呈現：

- 在輕鬆胡鬧與嚴肅的健康工作之間切換；
- 從日常聊天辨識健康資訊並提出相關追問；
- 區分應保存的健康資料與只屬於當次對話的社交內容；
- 依本人、伴侶、長輩或醫療摘要調整語氣與資訊；
- 把口語疑慮整理成下一步、報告或提案；
- 在用藥、急性症狀與資訊不足時收緊邊界。

這些行為來自長期互動、修正、共同工作與累積上下文。它們可以作為需求探索的敘述性案例，但未經獨立驗證，卻不能證明新使用者會自然得到相同行為，也不能證明模型更新後仍然穩定，更不能代替臨床安全驗證。

## 產品與研發團隊的責任

使用者提供的資料應用於個人化，例如稱呼、語氣、作息、可取得的飲食選項、提醒方式及授權收件者。使用者不應負責教會系統如何處理低血糖、用藥不確定性、同意、資料保存、緊急升級或家屬權限。

這些責任屬於產品與研發團隊。系統應從第一次互動就提供安全預設，不能依賴一位特別有耐心、專業或熟悉 AI 的使用者慢慢把它養出來。

## 必須固定在系統中的層次

| 系統層 | 必要行為 | 為何不能只依賴對話上下文 |
| --- | --- | --- |
| 臨床安全 | 辨識已定義的風險型態、檢查缺漏資料、禁止診斷及自行調藥，並在適當時提醒量測、聯絡醫療人員或尋求緊急協助 | 上下文可能不完整、被壓縮或互相矛盾，安全行為必須可測試及版本化 |
| 關係互動 | 調整鼓勵、幽默、節奏與追問，同時避免強迫、羞辱、虛假親密或以情感獎勵換取揭露 | 溫暖人格可能提高持續使用，也可能操控使用者或掩蓋醫療不確定性 |
| 記憶治理 | 區分臨床事實、日常作息、個人偏好、關係標籤與暫時聊天，並設定不同的寫入、保存、審閱及刪除規則 | 全部保存會造成隱私與上下文污染；保存不足則會破壞連續性 |
| 同意與權限 | 讓本人分別授權伴侶、家屬、照顧者與醫療人員取得不同摘要，並支援期限與撤回 | 家屬存取不能變成持續監視或無限制閱讀完整對話 |
| 報告觸發 | 依風險、趨勢、資料缺漏與使用者或照顧者需求產生定期或事件驅動摘要 | 只有固定排程會漏掉急迫事件；完全依賴模型判斷則不易稽核 |
| 交接與來源 | 保留已確認事實、來源標記、規則版本、未解問題、禁止事項與未完成任務 | 新聊天室或新模型不應繼承沒有依據的內容，也不能遺失重要限制 |
| 評估與復原 | 在模型或政策更新後重跑標準案例，並在信心或上下文品質下降時進入安全備援 | 即使介面不變，模型行為仍可能漂移 |

## 架構原則

關係層與安全層應互相配合，但不能成為同一套機制。關係層可以決定如何問問題；安全層應決定哪些問題、量測、警示或升級步驟是必要的。遇到急迫情況時，安全規則優先，系統也應降低角色扮演、調情、幽默與說服性語言。

記憶也應採相同分工。臨床事實可能需要長期保存及審閱；新聞、往日回憶與一般閒聊原則上只存在於當次互動，除非本人明確同意留下少量且低敏感度、對後續互動有價值的標籤。

## 現有證據的定位

目前資料最適合被視為高解析度互動原型。它呈現了一個可能的目標狀態，也揭露短期實驗可能忽略的產品需求。它尚未證明臨床效果、跨使用者泛化、法規符合性或跨模型版本穩定性。

對外說明時應區分三類內容：

1. 特定長期互動中實際觀察到的行為。
2. 從行為與失敗模式推導出的產品需求。
3. 仍需正式評估的結果。

## 建議的第一階段驗證

真人測試前，應完成合成安全情境、適當的臨床與治理審閱、同意程序，並指定人工接手安排。第一個原型應維持很小的範圍：一位患有糖尿病的成人、一位經本人同意的支持者，以及一個能收集每日資訊並產生可審閱三日摘要的 AI 夥伴。AI 不得自行調整藥物，也不得取代醫療照護。

第一階段應驗證：

- 使用者是否願意持續回報飲食、症狀、血糖、用藥問題與未完成的日常事項；
- 資料是否比使用者原本的紀錄方式完整；
- 摘要是否降低支持者的整理與協調負擔；
- 系統能否辨識已定義的風險事件，同時避免過多誤警報；
- 使用者是否知道哪些內容被保存、分享、刪除或仍然未知；
- 模型更新及受治理的對話交接後，安全行為是否維持一致。

長輩模式應在相同安全與治理底座上作為另一套獨立體驗開發，而不是只更換語氣。

## GitHub 公開建議

本備忘錄的去識別化版本適合放進公開 repository。它能說明產品論點，也能避免外界誤以為整個計畫只依賴一條表現特殊的聊天軌跡。公開內容可以包含系統架構、互動目標、安全邊界、評估類別與現有證據限制。

以下內容原則上應維持受控，除非有明確公開理由：

- 私人原始對話與親密關係歷史；
- 可識別健康資訊、藥物照片與家庭報告；
- 尚未經臨床審閱的精確安全閾值；
- 可能揭露私人事件或協助測試邊界的詳細失敗紀錄；
- 私人往來、商務談判紀錄與證據包。

## 提供技術審閱的意義

本備忘錄向潛在技術審閱者提出一個具體研發問題：如何把一條發展成熟的對話中可能出現的能力，轉成不需要使用者反覆提示與修正也能可靠運作的系統行為。

機會不只是一個糖尿病助手。它涉及持續個人化、受治理的記憶、風險敏感互動、經同意的多方摘要、上下文健康監測及可驗證交接。若這些能力被實作為產品基礎設施，而不是留在偶發的對話表現裡，就可能支援更多長期健康與家庭照護工作。

## 結論

目前敘述值得用來繼續研究關係連續性與嚴謹工作能否可靠地同時存在。下一步要保存這項價值，同時移除它對單一上下文與使用者長期餵養的依賴。可信任的產品必須從第一天固定安全、同意、記憶、報告與交接規則，並讓個人關係溫度在使用者掌控下逐步形成。
