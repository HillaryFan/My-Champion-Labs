# AI 健康照護夥伴主提案 V3

公開主提案 V3｜2026-09-20｜[English](../docs/main-proposal/MAIN_PROPOSAL_V3.md)｜[版本紀錄](../VERSION_HISTORY.md)｜[保留的 V2](MAIN_PROPOSAL_V2.md)

## 1. 一頁摘要

人不是活在表格裡。真正影響健康的資訊，常散落在一頓飯、一次手抖、一句「今天不太舒服」、忘記的藥、改變的作息，以及看似離題的日常聊天裡。要把這些片段整理成一份能拿去討論的紀錄，往往得靠本人回想，或由支持者重新問一遍、拼一遍。到了回診時，有些細節已經記不清楚。

**AI 健康照護夥伴不是另一個衛教聊天機器人，而是一個介於日常生活與正式照護之間、具有人性化互動並由本人控制的轉譯與協作層。**

我們希望讓人先照自己的方式說話，再決定哪些內容值得留下。AI 可以提出「我是不是聽到了一件需要記錄的事？」，由本人確認、修改或拒絕；經核准的少量資訊才進入紀錄，依授權整理成三日摘要或回診 brief。支持者與醫療人員看到的是有來源、能查證的重點，而不是整段聊天。

這個產品要驗證的價值，是讓三方少一點重複填寫、追問和翻譯資訊的工作。人性化互動讓人願意回來，本人的決定則控制什麼能被留下、交給誰。第一步從成人糖尿病相關日常紀錄的小範圍原型開始，再另行驗證長輩介面。目前是產品提案與驗證計畫，尚非已上市或通過臨床驗證的系統。

## 2. 尚未被完整承接的照護缺口

缺口不只是少一個提醒，而是生活經驗走到正式照護之前，還有一段沒被接好的路。本人可能在故事中提到不舒服，卻不知道哪個細節重要；支持者收到的訊息可能分散在不同時間；醫療端需要的是清楚的時間、來源和待確認問題，不是一篇把不確定性修飾掉的流暢摘要。

本案嘗試接起自然對話、候選訊號、本人確認、記憶分流、授權分享、安全切換與可查證報告。依[2026-09-17 的有限市場掃描](research/market-competitive-analysis/README.md)，我們尚未找到單一產品以公開資料展示這整套組合。這不是持續更新的全面市場調查，也不等於沒有競品或已建立商業護城河。

## 3. 現有產品類別各自解決了什麼、還缺什麼

市場上已有不少值得學習的工具。要問的是：它們是否已經接起這條由本人控制的完整流程，而不是把所有既有產品都說成不足。

| 既有類別 | 已承接的工作 | 本案還要回答的整合問題 |
| --- | --- | --- |
| 慢病教練 | 衛教、日常支持與結構化追蹤 | 能否接住零碎故事，再形成本人確認的紀錄，而不增加填表工作？ |
| 血糖紀錄與分享 | 量測、趨勢、報告與警示 | 能否保留生活背景，同時分清量測、本人說法和推論？ |
| 長者陪伴 | 對話、提醒與熟悉介面 | 互動之外，能否確實執行紀錄、分享與安全控制？ |
| 照顧者更新 | 把資訊送到支持者手上 | 本人能否選擇最小必要內容，而不是接受全天監看？ |
| 病歷代理存取 | 授權他人查看正式資料 | 尚未進入病歷的生活片段，如何先整理成有用的回診資料？ |

這些是整體流程的比較問題，不是斷言每家廠商都缺少每項功能。個別產品與查核限制仍以市場研究及來源紀錄為準。誰願意付費、整合成本多高、誰負責接手，也都還需要證據。

## 4. 產品核心主張

對話可以成為資訊入口，但不必因此變成無止境的蒐集。AI 先提出可能值得記錄的觀察，讓本人決定是否留下，才是這個設計的核心。它把非正式表達轉成別人能理解的資料，而不是把診斷藏在親切的對話裡。

如果本人少說第二遍、支持者少花時間拼湊、醫療人員更快找到需要問的問題，才可能形成產品價值。這些都要量測。本人點選確認，代表同意這樣記錄，不代表內容已經獲得醫療證實；記不清楚或說法有衝突的地方，應原樣保留。

## 5. 從日常聊天到本人控制的完整工作流

| 步驟 | 系統做什麼 | 本人保有什麼決定 |
| --- | --- | --- |
| 日常對話 | 承接飲食、作息、抱怨、故事和岔題。 | 自己選話題，也能拒答、暫停。 |
| 候選觀察 | 提出可能相關的片段，標示出處及不確定的時間。 | 先當作待確認內容，不直接寫成事實。 |
| 確認或修正 | 請本人確認、改寫、拒絕，或留待之後。 | 一般健康紀錄須經核准才寫入。 |
| 最小必要紀錄 | 只保存核准欄位，附來源、用途與版本。 | 周圍的閒聊不跟著整包留下。 |
| 授權摘要 | 產生可審閱的三日摘要或回診 brief。 | 決定對象、內容、涵蓋期間、用途與存取期限。 |
| 接收與查證 | 收件人看見來源、時間、缺漏、不確定性及待確認問題。 | 本人原話、量測、AI 推論、支持者註記與醫療確認分開呈現。 |
| 更正與交接 | 支援更正、撤回後續存取，以及授權範圍內的交接。 | 保留追溯，也如實說明已收取副本的刪除限制。 |

急迫協助走經核准的安全流程，不等待這套一般紀錄程序走完，也不等下一份摘要。若需要例外揭露，必須有另行審閱的依據，不能把「安全」當成全面取消同意的理由。

## 6. 三方各自得到什麼

| 對象 | 預期價值 | 如何知道是否真的有幫助 |
| --- | --- | --- |
| 參與者 | 不必像填研究表格一樣生活；能自然描述、確認紀錄、拒答、決定分享，也願意再回來說話。 | 操作與回報負擔、理解程度、更正率、自主感和持續互動意願。 |
| 家屬或授權支持者 | 不用全天監看、逐段拼湊訊息；收到本人核准的必要摘要，知道缺什麼、哪些問題要留到回診。 | 整理時間、有用的跟進、打擾程度與協作錯誤。 |
| 醫療端 | 不用讀完整聊天；取得結構清楚的回診 brief，辨認不同資訊來源與確認程度。 | 可讀性、查核及更正負擔，以及在經審閱流程中的實際用途。 |

減少臨床負擔仍是假設。一份摘要即使很受歡迎，只要讓醫療端多花時間查錯，仍可能是失敗的設計。

## 7. 人性化互動不是裝飾

人願不願意回來，會影響資訊能不能在生活中持續形成。熟悉的節奏、合宜的幽默、符合個人偏好的鼓勵，以及被適當記得的感覺，可能讓零碎或岔題的敘述比制式問卷更容易說出口。這是值得驗證的互動機制，還不是療效。

個人化應回應本人明確表達的偏好與真實行動。關掉人格設定、漏做一件事或拒絕回答，都不該換來冷淡或支持中斷。聊天次數不能直接當成健康成效；孤獨、羞恥、內疚、排他性與虛構感情，也不能拿來換取配合或資料。出現藥物、急症或安全問題時，安全框架立即取得最高優先權。

[產品化備忘錄](PRODUCTIZATION_NOTE.md)說明了這項分工：使用者提供偏好，研發團隊負責把安全、同意、記憶與復原做成可靠的產品能力。

## 8. 五層產品架構

| 產品層 | 在流程中的工作 |
| --- | --- |
| 陪伴層 | 提供容易使用的對話與語音，接住日常話題，適時追問並提出候選觀察。 |
| 人性化互動層 | 依本人選擇調整語氣、幽默、節奏、鼓勵與熟悉感，支持表達及再次使用。 |
| 安全層 | 執行經臨床審閱、可追溯版本的規則與人工接手路徑，風險出現時優先處理。 |
| 治理與 EIP 層 | 處理確認、選擇性寫入、存取範圍、保存、撤回、來源及規則版本；EIP middleware 仍是應用設計方向。 |
| 連續性層 | 產生經審閱摘要、回診資料，保留待確認問題並支援受治理的交接。 |

這五層是產品分工；產品化備忘錄的七項工程責任仍然保留。記憶及同意權限歸入治理，報告觸發與交接橫跨連續性、治理和安全，評估與復原則貫穿各層。這不是宣稱 middleware 已完成，也不構成 EIP 驗證。本案與 Oracle & Champion 仍是不同專案。

## 9. 成人與長輩介面分別驗證

成人原型先以一位同意參與的成人及一位授權支持者，測試有邊界的日常紀錄。語氣、提醒時間、說話速度、幽默，以及可選擇的親暱或調情風格，都由成年參與者主動選擇。AI 身分保持清楚，遇到醫療問題便暫停玩笑式互動。

長輩介面需要另行共創和驗證，不是替成人模式換個聲音。逐一了解聽覺、視覺、步調、生活習慣與支持安排；一次問一個必要問題，也容許岔題。被認可、自主、勝任感、連結與重要關係帶來的自豪，可以詢問，不能依年齡預設。避免幼兒化語氣、捏造家人的感受，或把反應較慢當成沒有決定能力。

沿用 V2 的回憶互動上限：最多每兩天主動邀請一次，可以跳過。完整故事暫時保留，只讓本人核准的一至三個低敏感標籤持續存在。新聞可以就是聊天；系統只用最小指標記住尚未問完的必要問題。故事裡若出現候選健康訊號，再另外請本人確認。

## 10. 同意、記憶分流、報告與交接

參與、人格設定、紀錄保存、偏好標籤、提醒、收件者與例外升級安排，各自提供清楚選擇。每位參與者有獨立紀錄和授權範圍；支持者身分本身不賦予完整存取或醫療權限。

| 資料類別 | 預定處理方式 |
| --- | --- |
| 閒聊、新聞、完整回憶 | 預設短暫保存，以實際驗證過的刪除控制處理，不列入一般報告。 |
| 核准偏好及少量標籤 | 用途明確，可以查看、更正和撤回。 |
| 已確認健康觀察 | 保存最少欄位、時間、來源、確認程度與未解衝突，另訂保存政策。 |
| 摘要與回診 brief | 限定授權期間與收件者，分開事實和推論，列出缺漏、不確定性及問題。 |
| 交接狀態 | 只帶走核准事實、來源、規則版本、權限、待辦與禁止事項，不繼承虛構關係或搬走整段聊天。 |

初期仍是七天成人原型、每三天一份由本人審閱的摘要。未來調整間隔或事件觸發，都要另行設定及審閱。送達失敗、無人回應、支援時段與替代路徑需事先定義；送出訊息不等於有人接手。

撤回可以限制後續存取，不能保證收件者手上的副本已消失。平台紀錄、備份、匯出、稽核保存與刪除機制，要驗證後才能向本人承諾。更正需保留適當追溯，也避免為了留痕而反覆複製敏感內容。詳細要求見[治理文件](../governance/GOVERNANCE.md)。

## 11. 安全與不可妥協邊界

這個夥伴協助溝通與整理，不取代醫師、護理師、糖尿病衛教師、緊急服務或個別照護計畫。它不診斷、不開藥、不自主調整藥物、不發明醫療閾值，也不為了聊完而延後求助。臨床規則需要合格人員核准，列明適用條件、來源、版本、排除情況、審閱日期與停用標準，更新後重跑測試。聊天可以改變偏好設定，不能自行學出新的治療規則。

玩笑、調情和角色扮演服從安全。不接受隱瞞 AI 身分、冒用權威、要求情感回報、排他依賴、羞辱或內疚式施壓，也不提供無限制監看。資料不足時，不能用安慰掩蓋不確定性。

漏掉安全切換、不當保證、延誤協助或未授權揭露，都要停下來審查。復原包含控制影響、適當人工檢查、權限修正及回歸測試。提示詞本身無法證明隔離、刪除、監測或緊急應變有效。真人使用前，必須具備經審閱的照護設定、同意及人工支援；尚無核准醫療設定時，不啟用疾病管理行動。

## 12. 現有證據、未知與驗證順序

目前有產品需求、有限市場研究，以及來源作者描述的長期互動原型觀察；尚無控制實驗療效結果或經核實的臨床部署。這些觀察用來提出測試問題，不足以證明跨使用者泛化、法規符合性或安全表現。[外部依據紀錄](../references/README.md)保留各來源的查核限制。

| 階段 | 要回答的問題 | 蒐集什麼 |
| --- | --- | --- |
| 合成情境 | 確認、權限、來源區分與安全優先是否真的有效？ | 候選紀錄錯誤、拒答處理、洩漏、漏報／誤報、中斷及復原。 |
| 經審閱成人原型 | 對話加三日摘要是否比本人原有方式更好？ | 必要欄位完整性、更正、本人與支持者時間、自主、理解及報告用途。 |
| 長輩獨立共創 | 介面是否令人自在、容易理解、操作得來？ | 尊重感、互動負擔、同意理解、接回未完成問題及短暫記憶行為。 |
| 重現與整合 | 換人、上下文衰退、模型更新及介接之後，價值能否保留？ | 固定案例重測、盲評摘要、控制穩定性、失敗率及營運成本。 |

先訂比較基準、指標與停止條件，再看結果。互動與預定的七／三十日留存，需和紀錄品質、安全及未來可能的臨床指標分開；七天原型本身無法證明三十日留存。失敗和額外查核工作要跟成功一樣記錄，不能預設會減少臨床負擔。

## 13. 平台需求與下一步

下一步需要做出本人控制的代理存取、確認後才寫入、依用途分開的記憶、可稽核規則、報告排程、送達確認與受治理交接。這些要靠平台功能與測試落實，不是再加長初始化指令。

先用合成案例定義候選觀察及摘要欄位，再測試確認、拒絕、更正、權限和安全切換。取得合格審閱與個別共創回饋後，才進入真人原型。摘要的價值若還不足以抵銷準備及查核成本，就先不擴張更多裝置、人格或機構介接。目前不宣稱任何平台合作或整合承諾。
